# Simulator screenshots

Part of the device testing guide ([device-testing.md](device-testing.md)).

**Retired from the ticket process on 2026-11-09.** The developer checks screens on the phone (`ticket-workflow.md`, step 7), so no ticket runs the simulator screenshot walk. A release runs it once, portrait, for the mockup drift check (`release.md`, step 1), and the script, the harness and these notes also serve a run the developer asks for and the reproduction below. The recipe for a story's visual criteria, and for checking a mockup against the app. `scripts/screenshots.sh` takes a screenshot of every screen on each simulator in the matrix (or on the simulators and clones `SHOTS_PLAN` names), in portrait, landscape and the largest text size (`accessibility-extra-extra-extra-large`), light appearance. Landscape runs on both simulators. (#109 concluded on 2026-10-30 that the iOS 26.5 simulator doesn't turn for the UI test, so its "landscape" shots were portrait, and skipped landscape there. #300 found on 2026-11-08 that it does turn: the run's log records "Interface orientation changed to Landscape Right", and its shots show landscape screens. #109's finding is superseded.) How landscape images are saved is in step 1:

**Reproducing a layout bug.** Diagnosis may use the simulator; the fix is still checked on the phone. Add a temporary method to `ShotsUITests` that launches the state (such as `launch(.sharing, standIn: "seeded")`), taps to the screen and calls `shot(...)`, run it alone (`SHOTS_TESTS=<method> SIMULATORS="iPhone 15 - iOS 27.2" SHOTS_VARIANTS=largest-text-landscape scripts/screenshots.sh`), and remove it afterwards. The harness rotates and taps for real, so the app's source stays as it is. It loads no seed set: make a seed's or a setting's state by tapping through the app, or in the harness's seed.

1. Run `scripts/screenshots.sh`. It writes `docs/screenshots/<today>/<simulator>/<variant>/<screen>.png` (git-ignored), the variant being `portrait`, `landscape`, `largest-text` or `largest-text-landscape`, or one of those with an `rtl-` prefix (below). A landscape image is saved 1178 × 2556, portrait-sized, with the EXIF orientation tag set to 8 (turn it to landscape), on both iOS versions (checked on 2026-11-08). Preview, Chrome and the image reader show it the right way up; a tool that ignores the tag, or reads the pixel size (`sips -g pixelWidth`), sees it sideways and portrait-sized. `scripts/contact-sheet.sh` sizes its sheet from the pixel size, so a landscape sheet is sized for portrait images (not fixed by #300). #109 probably took such an image for a portrait one. `SHOTS_OUT` changes the folder, `SHOTS_VARIANTS` runs fewer variants (`SHOTS_VARIANTS=portrait`), and `SIMULATORS` works as in `scripts/test.sh`. The simulators are shot at the same time, each one's variants one after the other, so a run takes as long as the slower simulator plus the build. `SHOTS_PLAN` gives each simulator its own variants, so different variants run at the same time (#301): entries `<simulator>=<variants>` separated by `;`, such as `SHOTS_PLAN="iPhone 15 Pro - iOS 26.5=portrait;iPhone 15 Pro - iOS 26.5=largest-text;iPhone 15 - iOS 27.0=landscape"`, which replaces `SIMULATORS` and `SHOTS_VARIANTS`. A simulator named again runs that entry on a clone of it, `<simulator> clone 1`, made when it is missing (`xcrun simctl clone`, which needs the source shut down: one that was booted is shut down for it, booted again, and stays booted, as `scripts/test.sh` leaves it) and reused after, kept on the Mac and shut down. A simulator has at most two clones, so three entries run at the same time; the fourth and later queue behind them, one after another, taking the lanes in turn. A variant named twice for one simulator is refused. The clone's images go in the simulator's own folder, its progress lines start with its own name, and `scripts/test.sh` never uses a clone: it looks simulators up by their exact names. `xcrun simctl delete "<simulator> clone 1"` removes one. Each simulator's progress lines start with `[<simulator>]`. The first failed test on any simulator stops every simulator's run at once, as soon as the test fails rather than when it ends, and the run lists the test, simulator and variant (#302). A run that keeps going past failures instead, such as a release run that wants them all at once, sets `SHOTS_KEEP_GOING=1`: every test runs and every failure is listed at the end. Each variant's folder is emptied first, unless `SHOTS_TESTS` names the tests to run (`SHOTS_TESTS="testSettings testForm"`): then the other tests' images stay, so one test can be rerun alone, and the run lists the images it wrote, since those kept may be older than the code.
   - Which variants: with no ticket order any more, a run the developer asks for names its own plan (`SHOTS_PLAN`, `SHOTS_VARIANTS`, `SHOTS_TESTS`). A full gate pass of every screen is three simulators side by side, each at Largest Text in landscape (with `SHOTS_KEEP_GOING=1`): `SHOTS_PLAN="iPhone 15 Pro - iOS 26.5=largest-text-landscape;iPhone 15 - iOS 27.2=largest-text-landscape;iPhone 15 - iOS 27.2=rtl-largest-text-landscape"`. A variant with the `rtl-` prefix runs the walk under Xcode's Right-to-Left Pseudolanguage (Brian's call, #122); right-to-left on iOS 26.5 and in portrait is given up until 1.10.0, when Arabic makes it matter.
   - A criterion about a transition, which no screenshot shows: record it with `xcrun simctl io <simulator> recordVideo <file>` and show the person, or check it on the phone. Say what a transition does only once it has been seen.
   - Why these two simulators: App Store Connect's beta testers (1.2.0, 2026-11-01) split evenly by device between iOS 26.6.x and iOS 27.0.1. iOS 27.2 is the nearest simulator to the second group. This Mac has no iOS 26.6 runtime, so iOS 26.5 is the nearest to the first.
   - Which tests a change needs: trace each changed view to the screens that use it, and from them to the `ShotsUITests` methods that reach them. A component in `App/Design/` is traced the same way, to its call sites. Add any screen that shows a string whose value changed. A change with no call sites to trace (the design tokens, a shared view modifier, or the harness's seed) has no list to trace: the ticket names the screens that cover each kind of use it affects, and the release's full walk covers the rest.
   - Resuming an interrupted walk (#488): the run keeps each test that passes in a ledger (`.build/screenshots-ledger`, git-ignored), by simulator and variant. `SHOTS_RESUME=1` with the same command skips those tests and keeps their images, running only the unfinished and failed ones. The ledger is used only if the app, the harness and `SHOTS_NOW` are unchanged, and a run without `SHOTS_RESUME` empties it. Interrupt a walk with Ctrl-C (or SIGINT): it cleans up the simulators as usual, and the tests that passed stay in the ledger.
   - Running the walk as if it were another time of day (#297): `SHOTS_NOW=HH:mm` (24-hour), such as `SHOTS_NOW=01:30 scripts/screenshots.sh`. The harness clock then reads that time today from each launch on, and keeps running, so every screen the walk reaches (the engine's statuses and day labels, My Day's "now" marker, the details page) shows that hour; it is how a bug that only shows near midnight is reproduced without waiting for the hour. It moves only the harness's clock: the system's own UI and the app's own `Date.now` (the New Reminder form's starting time) keep the real time. Without it the clock is the real one, as before. `testSeedHoldsAtAnyHour` runs in every walk and checks every seeded reminder's status, and the day of the ones due near now, at 12:30 AM, 1:30 AM, 8:20 AM and 11:50 PM, writing what each row said to `seed-statuses.txt` beside the screenshots. `SHOTS_NOW` always means today, so the daylight-saving case below reproduces only in the week after a change (it did on 2026-11-08, a week after 2026-11-01). Hours worth running a walk at: 12:30 AM and 11:50 PM (a due time before or after midnight), 1:30 AM (the hour a daylight saving change repeats), 8:20 AM (the mockup's). Why the seed holds at any hour: it places every time by wall clock, and a due time a week back was once placed by absolute minutes, which put the bins an hour late in the repeated 1 AM hour of the week after a change (#297).
   - Debugging a failed run: rerun only the failing test, on the one simulator and variant that failed (`SHOTS_TESTS`, `SIMULATORS`, `SHOTS_VARIANTS`). A row below the fold or a chip with no hit point fails only at the largest text (#116, three runs).
2. It builds a throwaway harness from `scripts/screenshots/` into `.build/screenshots`: the app's sources with a stand-in `@main` (`Harness/ShotsApp.swift`) over the test fakes and an in-memory store, seeded with the mockup's reminders, and a UI test (`UITests/ShotsUITests.swift`) that walks the screens. `SHOT_SCENARIO` picks the permissions, one test per scenario: everything allowed, first launch (onboarding), and notifications, alarms or Time Sensitive off (the banners).
3. The real app, its install and its data are never touched. The right-to-left variants change nothing on the simulator: the walk passes the pseudolanguage to the harness app as launch arguments (`-AppleTextDirection YES -NSForceRightToLeftWritingDirection YES`, the ones Xcode's scheme option passes), which last only that launch, and its swipes and side-dependent taps follow the direction. The harness has its own bundle ID, and it and its UI-test runner are uninstalled at the end, and each simulator's text size and appearance are put back, even after a failure, a stop at the first failed test, or an interrupt (the script stops every simulator's run first, then cleans up). The iOS 26.5 simulator's next boot after a stopped run sometimes still lists the UI-test runner in `xcrun simctl listapps` and `get_app_container`, though its bundle is gone from disk and the container path doesn't exist (#302, seen in 3 of 5 checks after a stop on iOS 26.5, in none of 4 on iOS 27.0; a run that ends normally wasn't checked). It is a stale record, not a leftover: to check an uninstall, look in the device's `data/Containers/Bundle/Application`.
4. Compare each screenshot with the mockup's screen. `scripts/mockup-shots.py <mockup folder> <out>` takes the mockup's screens under the same names, and `scripts/contact-sheet.sh` puts pairs side by side in one image to view. A screen the walk doesn't reach, add to `ShotsUITests` (and the seed, if it needs data), and to `mockup-shots.py`'s `SCREENS`.

What the harness can't do: the times are now plus or minus the mockup's gaps (or the chosen `SHOTS_NOW`'s), so they differ from the mockup's fixed 8:20 AM, and the system's own UI (notifications, the alarm, permission prompts) isn't in it.

A sideways drag on a list row with no action on that edge can act as a tap and open the row. In UI tests every right swipe did, at any speed, on Tags, Reminders and Settings on the iOS 27.0 simulator; on the iPhone (iOS 27.0.1) some did, on Tags and Reminders (#139). Apple's docs are silent. So a UI test that swipes right expects the row may have opened.

Two simulator quirks it works around (iOS 26.5 simulator, Xcode 27.1, seen before #109 skipped landscape there; #300 turned landscape back on there and hasn't rechecked them, and each one a run hits is fixed by the ticket that touches that screen): in landscape, a tap on a navigation bar button never lands and `swipeUp()` doesn't scroll, though rows and tabs take taps. So bar buttons are tapped after turning the phone to portrait and back, and scrolling is a coordinate drag. The simulator's first keyboard also shows a tip over the sheet, which the walk dismisses. That can't be undone: the tip doesn't come back on that simulator, for any app.
