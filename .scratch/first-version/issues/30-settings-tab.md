# Settings tab

Design spec: `docs/design/DESIGN.md` (Components: Settings row). Where it and the mockup disagree, see its Precedence note.

## What to build

Minimal Settings: status rows for notifications, alarms and Time Sensitive (from the adapters, with a way to open iOS Settings when denied: `UIApplication.openNotificationSettingsURLString` (iOS 16+) deep links to the app's notification settings, where the notification and Time Sensitive switches live; `UIApplication.openSettingsURLString` opens the app's page in Settings, which is the one to use for alarms. Pass the URL to `UIApplication.shared.open`. The docs say AlarmKit authorization can be changed in the Settings app but don't name the screen: check on a device which link lands where), **Send a Test Nudge** (a real nudge through the adapters, so the person can check it works), and **Delete All Data** (confirmation, then ticket 17's delete-all and cancel of everything pending). Also a link to How It Nudges (ticket 31).

## Acceptance criteria

- [x] Status rows reflect fake permission states in a test (allowed, denied, not determined).
- [x] Denied rows offer an Open Settings action that uses the URL strings above (assert the URL, not the system behavior); on a device it lands on the right Settings page (human check). *(One row, as the mockup draws it; see Comments.)*
- [x] Send a Test Nudge schedules one notification through the notification adapter, which Done removes. *(Reworded, agreed 2026-10-19: it was "one nudge via the plan path and is cancelled by Done". There is no reminder, so there is no plan item; see Comments.)*
- [x] Delete All Data requires confirmation; after it the store and all pending items are empty.
- [x] Matches the mockup's Settings screen.

Blocked by: 21, 23

## Comments

**Decisions (2026-10-19), settled with the user before coding.** Apple's docs, read through apple-rag, confirm `openNotificationSettingsURLString` (iOS 16+) "deep link[s] to your app's notification settings" and `openSettingsURLString` opens "your app's custom settings". Neither says what is on those pages, so both were device checks.
1. **Send a Test Nudge** is one ordinary notification (identifier `test-nudge`, an interval trigger 5 s out, the `nudge` category so it offers Done, no reminder ID), added by `NotificationAdapter.sendTestNudge()`. It is no reminder's, so the engine and store know nothing of it, and criterion 3 was reworded (above). The `nudge.` prefix means no plan removes it, and the adapter's 64-pending room already counts other requests. It uses no alarm. The system clears a notification when its action is chosen, and Done on it reaches no reminder (`deliveredNudge(in:)` is `nil`, tested). Row: disabled when notifications are off, and a "Sent" label for 6 s after the tap (not in the mockup; without it nothing shows for 5 s).
2. **Delete All Data**: `AppModel.deleteAllData()`, not through `perform` because the store goes first and aborts. Order: `store.deleteAllData()`, then a **fresh engine** whose empty plan reaches both adapters (not emptied lists: the old engine keeps a key for every history and its alarm-limit records), then `waitUntilApplied()`, then `NotificationAdapter.cancelAll()` (pending including the test nudge, and every delivered nudge). A store that turns the delete down changes nothing, and the screen says "Couldn't Delete Your Data". A failed alarm cancel after the data is gone is cleared by the next App opened. An alarm that is ringing is left to ring, as any re-plan leaves it. Confirmation is an alert, as Tags' delete is (a dialog from a button is a popover with no Cancel on iOS 26).
3. **How It Nudges link:** left to ticket 31, which builds the screen and already names the link. The mockup's Settings has no such row.
4. **Open iOS Settings** is one row (the mockup's layout), shown when notifications, Time Sensitive or alarms is off. Alarms denied (alone, or with notifications) opens the app's page (`openSettingsURLString`); notifications or Time Sensitive off opens the notification settings (`openNotificationSettingsURLString`). Alarms "not determined" reads "Not Set" with no row, since onboarding asks (31). The footer is built from `Engine.reach`, one sentence per urgency, so no rule is repeated. It drops the mockup's "every minute, up to 10 times": that is mockup data, not the engine's.

**What is not here (ticket 31):** the permission banner the mockup shows under Settings' title, the How It Nudges link, and any request for permission. The Settings tab can be reached with permissions that were never asked for, so the device checks used a temporary test (since deleted) to raise the prompts.

**Found on the phone, and fixed here: Alarms went stale.** Alarms turned off in iOS Settings while the app was suspended sent no `authorizationUpdates` event (the log showed only the initial `authorized`), so the Alarms row, and the plan, stayed on allowed until a relaunch. A read of AlarmKit's state off the main thread answered `denied` at once. So `AlarmAdapter.refreshAuthorization()` now reads again on each App opened, and AGENTS.md's AlarmKit paragraph and `SystemAlarmManager`'s comment say so (approved by the user, who had set the "read once" rule in ticket 21). Guards, each mutation-checked: no second read while one is outstanding (a read can hang, and once froze the main thread); an update or the prompt's answer that comes while a read waits wins over it; a read that times out leaves the state alone. Notifications and Time Sensitive were already re-read on every App opened.

**Tests.** `SettingsStatusTests` (9: rows, URL choice, footer sentences, test-nudge enabled); `TestNudgeTests` (5); in `AppModelTests`: delete-all empties store, engine and both adapters, takes new reminders afterwards, a store that can't delete (a read-only file) changes nothing, before launch does nothing, the test nudge survives a plan, the rows through the fake adapters (3 cases), and alarms turned off with no update are found on App opened; in `AlarmAdapterTests`, three for the refresh. Totals: 231 engine tests, 265 app tests on iOS 26.1 and on 26.5. Red first throughout; mutation-checked: the store-first order, and each refresh guard. `FakeNotificationCenter` gained the two remove-all calls and `FakeAlarmManager` a gate to finish a read late.

**Screenshots** (iPhone 17 simulator, iOS 26.5, a throwaway project over the repo's `App/` sources with fake adapters): everything on, alarms off, Time Sensitive off, everything off, the largest text size (rows stack), and dark. Compared with the mockup: the three tiles' colors and glyphs, the section titles and footers, the chevron on Open iOS Settings, the gray Send a Test Nudge when notifications are off, and the destructive Delete All Data all match. Rows sit at the system's height (my own 44 pt minimum doubled it). Landscape was not screenshotted; `TabScreen` centers the content as on the other tabs.

**Device (Brian's iPhone, iPhone 15, iOS 27.0.1).** Nudge-inator was not installed before; it was uninstalled after (`xcrun devicectl device info apps` lists none), and the temporary prompt test was deleted. Brian allowed both prompts and put every setting back. Each check below was done by hand, one at a time.
1. **Everything on:** Notifications On, Alarms On, no Open row, Send a Test Nudge enabled, footer as built. Passed.
2. **Send a Test Nudge:** the "Test nudge / Nudges will look like this." banner came 5 s after the tap with the app in front and with the phone locked, and Done cleared it each time. "Sent" showed. Tapping the notification opened the app. Passed.
3. **Alarms off in iOS Settings** (the app's page): "Open iOS Settings" opens Nudge-inator's own page in Settings, where the Alarms switch is. First run: turning alarms back on did not reach the app (above). After the fix: Off and On both showed within about 2 s, no relaunch. Passed.
4. **Time Sensitive off:** Notifications "On · Time Sensitive off" in red, the footer said High comes as ordinary notifications, and Open iOS Settings landed on Nudge-inator's **Notifications** page. Passed.
5. **Allow Notifications off:** Notifications Off, Send a Test Nudge disabled, the footer the one line, and Open iOS Settings landed on Nudge-inator's Notifications page. Back on: everything returned. Passed.
6. **Delete All Data:** a tag and a Relentless Break Through Focus reminder due in 4 min; Cancel kept both; Delete emptied Now, My Day and Tags; no notification came over 6 min; then `AlarmDeviceCheck`, which requires the app to hold no alarms, passed. Passed.

**Not verified.** Both denied at once: the row opens the app's page, the URL check 3 covers, but the combination was not run. Landscape and VoiceOver on the Settings rows were not checked on the phone (VoiceOver reads each row as one element, "Notifications, On"; the "Sent" label is not announced). The 6 s "Sent" label and the footer wrapping at the default size (Notifications' status wraps onto two lines) are as drawn, not in the mockup.

**Code review** (standards and spec, two agents; then a scoped re-review of the alarm refresh). Fixed: the engine was built twice the same way (`makeEngine`); the 6 s "Sent" delay was tied to the 5 s trigger by a shared constant; a vacuous Done test now asserts the nudge is `nil` first; the criterion-1 test now goes through the model with fake adapters; `SettingsRow` got previews; the unneeded `state == .ready` check on the two actions (the unreadable store already shows instead of the rows); a comment typo; the read's comment now says `nil` also means "one is outstanding"; and the mid-read test now proves the update landed first. Kept: the footer wording and the missing banner (above); `previewPermissions` and `previewReach` as init parameters, as the other tabs take their preview engines; `OpenSettings.urlString` as a string, as the ticket names the strings. Not changed: the first launch read can return `nil` instantly if a refresh overlaps it, so a plan reads alarms as not asked until the next App opened, which plans as allowed anyway; and a slow read delays App opened's re-plan by up to the 2 s limit.
